# 32 MiBのテストファイルを扱う設計案

状態：提案。
ケース名と左右のエディタは実装済みだが、この文書のS3転送と32 MiB上限は未実装である。
現在の保存上限は引き続き各入力と期待出力が64 KiB、全体が256 KiBである。

## 保存先と圧縮形式

テストの本文はS3へ保存し、RDSには名前、順序、サイズ、チェックサム、保存先、検証状態と公開版の対応だけを保存する案を推奨する。
これは[ADR 0003](../adr/0003-store-test-sets-in-amazon-s3.md)の方針を具体化したものである。
現在の実装は下書き、公開版、提出ごとの採点要求へ入出力をコピーするため、大きなデータでは同じ内容が繰り返しDBへ保存される。
S3への参照を固定する方式へ移すと、提出ごとのテスト本体の複製を避けられる。

S3へ移すことと、ZIPにまとめることは別の判断になる。
編集時と採点時では必要な取得単位が異なるため、次のように分ける。

| 用途 | 保存単位の案 | 理由 |
| --- | --- | --- |
| 編集中 | 入力と期待出力をそれぞれ独立したオブジェクトにする | 一つの入力の変更で全ケースを再送しない |
| 公開済みの採点用データ | グループごとの`tar.zst`とマニフェスト | 既存ADRに合わせ、取得回数と不要な転送を抑える |
| 一括取り込み | 必要になった段階でZIPを受け付ける | 手元で作成した複数のファイルを取り込む用途に使う |

初期のUI編集にZIPは必須にしない。
公開処理で採点用バンドルを生成すれば、ブラウザーに全ケースの圧縮と再アップロードを要求せずに済む。
ZIPを採点用形式にも採用する場合はADR 0003の変更になるため、圧縮時間、展開時間、転送量を実データで比較してから決める。
未計測の圧縮率を、サイズ制限や一時領域の計算に使わない。

## 大きさの契約

ユーザーが指定した「1ファイルあたり32 MB程度」は、圧縮前のUTF-8バイト数で**32 MiB（33,554,432バイト）**と定義する案である。
入力と期待出力は別ファイルなので、ケース一つで最大64 MiBになる。
行数や整数の個数では制限しない。
たとえば20万個の10桁の整数を一文字の区切りで並べると、およそ220万バイトとなる。

全ケースの合計にも上限が必要になる。
100ケースの入出力すべてが上限に達すると6.25 GiBになるため、まずテストセット全体を圧縮前1 GiB、採点用バンドルを展開後128 MiBまでにする案とする。
ケース数の上限はTLに関係なく100件とする。
これらの合計上限は未確定であり、実際の問題データと採点時間を確認して調整する。

## 転送と公開

Lambdaの同期呼び出しのペイロード上限は6 MBなので、32 MiBの本文を現在のJSON APIへ含める構成では扱えない。
圧縮で6 MB以内になる保証も置けないため、本文はブラウザーからS3へ直接送る。
APIは権限確認とアップロード先の発行、完了の確定を担当する。
根拠は[AWS Lambdaの呼び出し仕様](https://docs.aws.amazon.com/lambda/latest/api/API_Invoke.html)にある。

1. 作成者がケースを選び、名前と入出力を編集するか、入力ファイルと出力ファイルを選択する。
2. APIが問題の所有者、下書きの更新番号、宣言サイズを確認し、新しいファイルIDと署名付きアップロード先を発行する。
3. ブラウザーが変更したファイルだけをS3へアップロードする。
4. 完了要求を受けたサーバーが実際のサイズ、内容のチェックサム、UTF-8、NUL不在を検証する。
5. 検証済みのファイル参照を、更新番号を条件として下書きへ保存する。
6. 公開時にマニフェストと採点用バンドルを生成する。
7. 全バンドルの検証と保存が完了してから、公開版の参照を一度のDBトランザクションで切り替える。

32 MiBでは単一のアップロードを初期案とする。
回線切断時の再開が必要になればマルチパートを追加する。
AWSは一般に100 MB以上でのマルチパート利用を推奨しているが、不安定な回線ではそれより小さくても再送単位を分割する利点がある。
根拠は[S3のマルチパートアップロード](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)にある。

署名付きURLは有効期間内に繰り返し使えるため、URLの発行を「一回だけ書ける権限」とは扱わない。
検証したS3 Version IDとSHA-256を固定し、その後のアップロードが既存の下書きや公開版を差し替えないようにする。
署名時にチェックサムを固定する方法と、検証処理で実データを計算する方法を組み合わせる。
この性質は[S3の署名付きURL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)で確認できる。

公開準備に失敗した場合は、以前の公開版で採点を続ける。
所有者の変更、古い更新番号、検証中のファイルを含む公開要求は拒否する。
未完了アップロードと参照されなくなった下書きファイルには削除期限を設けるが、公開版や提出が参照するデータは削除しない。

ZIP取り込みを加える場合は、圧縮後サイズだけでなく、展開後の一ファイルサイズ、合計サイズ、ファイル数を検証する。
パストラバーサル、リンク、重複パスも拒否し、ケース名をそのまま保存パスとして使用しない。

## DBに残す情報

ケース名は表示用の文字列とし、ファイルIDやS3キーから分離する。
名前を変えてもデータ本体の再送は不要にする。

- ケース：固定ID、名前、順序、入力ファイルID、期待出力ファイルID。
- ファイル：所有者、S3キー、Version ID、SHA-256、圧縮前サイズ、検証状態。
- テストセット：固定ID、ケース構成、採点用マニフェストとバンドルの参照、準備状態。
- 問題：下書きが参照するケース構成、公開版が参照するテストセットID。
- 提出：問題の公開版、テストセットID、ランタイムID。入出力の本文は持たない。

公開テストセットの内容は変更しない。
同時編集の競合は現在と同じ更新番号で検出する。
ブラウザーから受け取ったS3キーをそのまま採用せず、所有者に紐づいたファイルIDをサーバー側で解決する。

## エディタとジャッジの変更

32 MiBの対応では、テキスト欄の上限変更だけでなく次も実装する。

- ブラウザーでは選択中のケースだけを読み込み、大きなファイルは選択アップロードと限定プレビューを提供する。
- 行番号は見えている範囲だけを描画する。本文の編集性能は長い一行と20万行の両方で測る。
- 本文全体のJSON化、毎キー入力での全ケース再送、sessionStorageへの本文キャッシュをやめる。
- 小さな編集は従来の自動保存を維持し、大きなファイルはアップロード中、検証中、保存済みを区別する。
- ジャッジは入力と期待出力をファイルとして順次取得し、標準入力への転送と出力比較をストリームで行う。
- 現在1 MiBの標準出力上限も32 MiBへ拡張し、出力ファイルの上限超過とストレージ不足を区別する。
- コンパイル成果物、展開中のバンドル、入力、期待出力、ユーザー出力が同時に存在する分の一時領域を確保する。
- 既存のDB内ケースは、移行完了が確認できるまで残す。既存提出が参照する旧データを先に削除しない。

受け入れテストには、32 MiBちょうどの成功、32 MiB+1バイトの拒否、20万個の整数、20万行、長い一行を含める。
通信中断、検証後の再アップロード、同時編集、公開切り替え失敗、秘密テストへの権限確認も検証する。
