# ADR 0009: 提出と同じ言語群で対話用ジャッジを実行する

- 状態: Accepted
- 決定日: 2026-09-13
- 範囲: isolateワーカーへの実装。公開前に実機検証を行う

## 背景

提出プログラムからの質問に応答する問題は、提出終了後に出力を検証するスペシャルジャッジでは扱えない。
作問者が応答と正誤判定を記述するプログラムを、**対話用ジャッジ**と呼ぶ。
利用者とは、対話用ジャッジにも提出で使える言語群を提供する方針を合意した。
以下の設計を採用し、実機での検証に合格してから公開する。

## 決定

### 言語と問題設定

対話用ジャッジは提出受付時に公開されている言語から選び、提出側とは独立して指定する。
既存のランタイム一覧とコンパイル処理を共用し、対話用に独自の言語一覧を作らない。
現在の公開対象はC23のGCCとClang、C++23のGCCとClang、CPython 3.14、PyPy 3.11、Codon 0.20、Rust 2024である。
JavaとC++17の公開保留を維持する。

問題の判定方法に対話形式を追加する。
対話用ジャッジのソース、言語、テストケースを公開版に含め、提出受付時に同じDB操作で固定する。
通常判定とスペシャルジャッジに対話用ジャッジを重ねて実行しない。
未公開の問題は、作問者の試験提出で確認できるようにする。

### 実行と判定

提出と対話用ジャッジを別々のisolate環境で同時に実行し、管理ワーカーが標準入出力を双方向に中継する。
ケースごとに異なるbox ID、UID、cgroupと作業領域を使い、相手側のファイルを公開しない。
採点全体の同時実行数は1提出のままとし、2つのコンパイルは順番に行う。

対話用ジャッジは標準入力から提出の発言を読み、標準出力で応答する。
終了コード0を正解判定とし、非ゼロ終了とシグナル終了をWAとして扱うことで、`assert`を使えるようにする。
ACには提出側の正常終了も必要とする。
対話用ジャッジのコンパイル失敗と資源制限超過はJEとし、提出側の失敗と区別する。
一方の終了に伴って管理側が停止した相手のシグナルを、新たな失敗として扱わない。
対話の終了順序と時間切れの扱いは[仕様](../judge/interactive-judge.md)に記載する。

### メモリの配分

対話用ジャッジの実行メモリを提出側より小さくし、2 GBのLightsail上で管理処理の余地を確保する。
既存のワーカー全体の上限は1,536 MiBであり、両方を512 MiBにすると管理処理に残る差分は512 MiBになる。
管理処理には中継バッファ、入力と成果物のコピーがあり、作業用tmpfsもメモリを使う。
この差分をすべて空きメモリと見なすことはできない。

対話用ジャッジを256 MiB、提出側を従来の512 MiBとする。
コンパイルは並列化しないため、各1 GiBを維持する。
128 MiBへの縮小は、インタプリタや採用ライブラリのための余地をさらに減らすので採用しない。
通常のスペシャルジャッジは逐次実行のため、既存の512 MiBを変更しない。

256 MiBで公開中の全言語を利用できるかは未検証である。
公開前に言語ごとの起動と採用ライブラリ、両側が上限付近まで使うケースを実機で確認する。
確認できなければ、その言語だけを黙って対象から外さず、メモリ配分か実行基盤を再検討する。

### 診断の公開範囲

対話履歴と対話用ジャッジの標準エラーには、非公開のテスト情報が含まれ得る。
保存量を制限し、問題作成者自身の提出詳細だけに返す。
提出一覧と第三者への応答には含めない。

## 代替案

提出と対話用ジャッジを同じサンドボックスで動かす案は、非公開の入力や判定コードを提出から参照できるため採用しない。
対話用ジャッジをC++だけに限定する案は、同じ言語群を使う要件を満たさない。
実行メモリを両側とも512 MiBにする案は、管理処理を含む同時実行の実測がない段階では選ばない。
