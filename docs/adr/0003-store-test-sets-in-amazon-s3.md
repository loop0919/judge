# ADR 0003: テストセットをAmazon S3へ保存する

- 状態：Accepted
- 決定日：2026-09-03
- 変更：採点時の取得主体と実行環境は[ADR 0005](0005-use-firecracker-and-isolate-on-ec2.md)で置き換え、その実行基盤を[ADR 0006](0006-use-lightsail-and-isolate.md)で変更。保存形式と取り込み用の検証タスクは維持する。

## 背景

ユーザーが作成する問題には、`N <= 10^6`のように大きな入力を扱うものがある。
入力と期待出力をPostgreSQLへ格納すれば、問題情報と同じトランザクションで管理できるものの、テストデータの更新がWAL、レプリケーション、バックアップの容量を増やす。
採点時には完全なファイルとして順次読み出すため、RDBの検索機能も生かせない。

テストデータをAmazon S3へ移すだけでは、保存単位が決まらない。
一つのテストケースを一つのオブジェクトにすると、ケース数に応じて取得回数と待ち時間が増える。
反対にテストセット全体を一つのアーカイブにすると、最初のグループで採点を終了できる場合にも全量の取得と展開が必要になる。

採点結果には再現性も要る。
問題公開後に同じS3キーの内容を置き換えると、過去の提出が参照したテストデータを特定できなくなる。
さらに、問題作成者がアップロードするアーカイブは、パストラバーサルや過大な展開サイズを含む可能性があり、未検査のままジャッジへ渡せない。

## 要求

- 大きな入力と期待出力を、RDBのバックアップとレプリケーションから分離できること。
- 過去の提出が使用したテストデータを一意に特定できること。
- 問題作成者から受け取ったデータを、採点に使う前に検査できること。
- Fargateタスクのメモリへテストデータ全体を読み込まずに採点できること。
- ケース数が増えても、S3への取得回数がケース数に比例しないこと。
- 秘密テストケースをユーザープログラムと外部の利用者へ公開しないこと。

## 検討した選択肢

### PostgreSQLへバイナリとして保存する

問題リビジョンとテストデータを同じデータベースで管理できる。

しかし、大きな入力と期待出力はWAL、レプリケーション、バックアップへ複製される。
採点処理はファイル全体を順次読むため、RDBへ格納する費用に見合う検索上の利点もない。

### 一ケースを一つのS3オブジェクトとして保存する

必要なケースだけを取得でき、ケース単位の差し替えも容易になる。

しかし、ケース単位の差し替えはテストセットの再現性と衝突する。
ケースが増えるほどS3への取得回数も増え、短いケースではオブジェクト取得の待ち時間が採点時間へ占める割合も大きくなる。

### テストセット全体を一つのS3オブジェクトとして保存する

採点タスクごとの取得回数を一回に抑えられる。

しかし、一部のケースだけを実行する場合や途中で採点を終了する場合にも、テストセット全体を取得して展開する必要がある。
テストセットが大きくなるほど、この不要な転送と一時領域の消費を無視できない。

### テストグループごとにS3オブジェクトを分ける

部分点や制約に対応する論理グループを単位として取得できる。
大きなグループを上限サイズで分割すれば、ケースごとの取得回数と全量取得の双方を避けられる。

RDBへテストセットの識別子、S3オブジェクトのバージョン、チェックサムを保存すれば、オブジェクトストレージを使いながら採点条件を固定できる。

## 決定

入力、期待出力、マニフェストからなるテストセット本体をAmazon S3へ保存する。
PostgreSQLには、問題リビジョンとテストセットの対応、保存場所、S3 Version ID、チェックサム、サイズ、ケース数、状態を保存する。

一つのテストセットには変更されない識別子を割り当てる。
公開済みのテストセットは上書きせず、内容を変更するときは新しいテストセットを作成する。
Submissionは採点時に使用した問題リビジョンとテストセットの識別子を保持する。

S3バケットではVersioningを有効にする。
採点可能になったオブジェクトには一意なキーを割り当て、通常の運用権限では上書きと削除を許可しない。
PostgreSQLにはキーだけでなくS3 Version IDとSHA-256チェックサムも保存する。

S3上では、次の構造を基本とする。

```text
problems/{problem-id}/revisions/{test-set-id}/
├── manifest.json
└── groups/
    ├── sample.tar.zst
    ├── main-001.tar.zst
    └── main-002.tar.zst
```

各バンドルは、部分点や制約に対応するテストグループを単位とする。
一つのグループが大きい場合は、設定した展開後サイズを超えない複数のバンドルへ分割する。
具体的な分割サイズは、S3の取得時間、展開時間、Fargateの一時領域を計測して運用仕様で定める。

`manifest.json`は、少なくとも次の情報を持つ。

- フォーマットのバージョン。
- テストセットの識別子。
- バンドルの実行順序。
- 各バンドルのS3キー、S3 Version ID、SHA-256チェックサム、圧縮後サイズ、展開後サイズ。
- 各ケースの名前、入力ファイル、期待出力ファイル、所属グループ。
- 部分点を採用する場合の配点。

マルチパートアップロードのETagは、オブジェクト全体のMD5とは限らない。
そのため、内容の同一性をETagだけで判定せず、アップロード時と採点時にチェックサムを検証する。

## 取り込み

問題作成者は、API Lambdaを経由せず、署名付きURLを使って隔離用S3バケットへテストデータをアップロードする。
大きなファイルにはマルチパートアップロードを使う。

アップロード直後のテストセットは採点に使用しない。
ユーザーコードを実行しない専用のFargate検証タスクが、少なくとも次の条件を検査する。

- 絶対パスと`..`を含むパスがないこと。
- シンボリックリンクとハードリンクがないこと。
- ファイル数、圧縮後サイズ、展開後サイズが上限内であること。
- 各ケースに入力と期待出力がそろっていること。
- ケース名とファイル名が重複していないこと。
- マニフェストが参照するファイルだけを含むこと。

検証タスクは、受け取ったファイルを正規化された`tar.zst`へ再構成し、チェックサムを計算して採点用S3バケットへ保存する。
すべての検査と保存が成功した場合に限り、PostgreSQL上のテストセットを`READY`へ遷移させる。
隔離用バケットの不完全なアップロード、拒否したデータ、処理済みデータは、Lifecycleルールで期限後に削除する。

## 採点時の取得

Launcher Lambdaは、対象テストセットのマニフェストと必要なバンドルに対して、有効期間の短い署名付きGET URLを発行する。
ジャッジ用Fargateタスクには、テストケース用S3バケットを読み取るTask Roleを付与しない。
タスク内のユーザープログラムがTask Roleの資格情報へ到達した場合に、別の問題の秘密テストケースまで取得できるためである。

`judge-runner`はコンパイル後、各グループの実行直前に、そのグループで必要なバンドルをFargateの一時領域へダウンロードする。
取得したオブジェクトのS3 Version ID、サイズ、チェックサムをマニフェストおよびPostgreSQLの記録と照合してから、ユーザープログラムを開始する。
途中の判定結果によって採点を終了できる場合は、後続グループのバンドルを取得しない。

ダウンロード、展開、入力、出力比較はストリーミング処理とする。
テストデータ全体を`judge-runner`のメモリへ保持しない。
期待出力はユーザープロセスから読み取れない領域へ置き、入力は`judge-runner`が開いたファイルを標準入力として渡す。

Fargateの一時領域には、コンテナイメージ、テストデータ、コンパイル成果物、ユーザー出力が共存する。
テストセットの展開後サイズ上限は、これらの合計と安全余白がタスクの一時ストレージへ収まる値に設定する。

## 影響

テストデータの増加はPostgreSQLのWALとバックアップ容量へ直接加算されなくなる。
バンドル単位で取得するため、ケース単位のオブジェクトより取得回数を抑えながら、不要なグループの転送を避けられる。

問題とテストセットのリビジョンが固定され、過去の提出が使用したS3オブジェクトをVersion IDとチェックサムで特定できる。
一方、テストセットの訂正でも新しいリビジョンが必要になり、既存の提出をどの条件で再採点するかを運用側で決める必要がある。

隔離用バケット、検証タスク、採点用バケットが増える。
署名付きURLが有効なあいだに漏えいすれば対象オブジェクトを取得できるため、URLをユーザープロセスへ継承せず、ログにも記録しない実装が必要になる。

## 未決事項

- テストセット、バンドル、単一ケースに許可する圧縮後サイズと展開後サイズ。
- 一つのバンドルへ含めるケース数と目標サイズ。
- 署名付きURLの有効期間と、取得失敗時の再発行手順。
- ユーザープロセスからネットワーク、資格情報、テストデータを隔離する具体的な実装。
- 公開済みテストセットを訂正した場合の再採点方針。
- 採点用テストセットと隔離用データの保持期間。
