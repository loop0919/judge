# ADR 0005: EC2上のFirecrackerとisolateで採点する

- 状態：Superseded by [ADR 0006](0006-use-lightsail-and-isolate.md)
- 決定日：2026-09-11
- 置き換え対象：[ADR 0001](0001-use-aws-fargate-for-judge-execution.md)、[ADR 0002](0002-standardize-judge-task-resources.md)
- 一部変更：[ADR 0003](0003-store-test-sets-in-amazon-s3.md)の採点時の取得主体と実行環境

## 背景

公開サービスでは、信頼できない提出コードを実行し、子孫プロセスを含む実行時間と最大メモリ使用量をケースごとに記録する必要がある。
Fargateを採用した当初はホスト管理の削減を優先したが、採点プロセスの隔離、cgroupの管理、制限超過時の回収を自分たちで制御できる構成へ変更する。

ローカル開発用のDockerワーカーは、コンパイルと提出処理の動作確認に使用している。
コンテナの開始終了時刻を使う現状の実装は、提出プロセス群のCPU時間と最大メモリ使用量を記録する本番実装とは区別する。

## 検討した選択肢

### EC2上でDockerまたはisolateだけを使う

isolateは競技プログラミング向けに、プロセスの隔離、リソース制限、計測機能を提供する。
ただし、ホストと提出コードがカーネルを共有するため、カーネル侵害時にはホストや別の提出へ影響が及び得る。
不特定多数の提出を処理する本番の隔離境界としては採用しない。

### AWS Fargateを継続する

提出単位でタスクを廃棄でき、ホストOSの管理を減らせる。
一方、採点用のcgroupと隔離機能を制御する自由度が限られるため、今回の計測方式には採用しない。

### EC2上のFirecrackerとVM内のisolateを組み合わせる

Firecrackerで提出ごとにゲストカーネルを分離し、ゲスト内のisolateでケースごとのプロセス群を管理する。
ホストからの隔離と採点用の計測を別の層へ分けられるため、この構成を採用する。

## 決定

EC2上で提出ごとにFirecrackerのmicroVMを作成する。
VM内ではisolateのcgroupモードを使用し、コンパイル用とケースごとのサンドボックスを分ける。
コンパイルは一提出につき一回とし、成果物だけを読み取り専用で各ケースへ渡す。
採点終了後はVMと提出専用の書き込み領域を廃棄し、別の提出へ再利用しない。

CPU時間、経過時間、最大メモリ使用量をケースごとに記録する。
CPU時間を採点上の実行時間とし、経過時間には待機や停止を回収するための別の上限を設ける。
メモリはケース専用cgroupのピーク値で計測し、制限と計測の対象に子孫プロセスを含める。
コンパイルとVM起動はケースの実行時間へ含めない。

ADR 0002のFargate向けの1 vCPUと2 GiBは引き継がない。
EC2のタイプ、VMのCPU数とメモリ、同時実行数は実機検証後に固定する。
既存の本番方針であるユーザープロセス群の512 MiB上限は維持し、コンパイル用の上限は別に決める。
VM全体にはゲストOSと採点制御が動作する余白を確保する。

## 管理ワーカーと提出環境の境界

EC2上の管理ワーカーが採点キューを受信し、ソースコードと必要なテストデータを取得する。
ゲストにはネットワークインターフェースを付けず、AWS認証情報、署名付きURL、期待出力を渡さない。
入力と結果は用途を限定したホストとゲスト間のチャネルで転送し、出力比較は管理側で行う。
ゲストからのメッセージは信頼せず、長さ、形式、提出とケースの対応を検証する。

Firecrackerはjailerを通して起動し、ホスト側にもCPU、メモリ、I/Oの上限と監視期限を設ける。
提出プロセスには管理ソケット、計測結果の書き込み権限、ホストのディレクトリを公開しない。
EC2はAPIとDBから分離し、管理ワーカーのIAM権限と通信先を必要な範囲へ限定する。

## ADR 0003との関係

S3への保存、Versioning、チェックサム、バンドル単位の取得、取り込み時の検証は維持する。
採点時のLauncher LambdaとFargate内のダウンロード処理は、EC2上の管理ワーカーによる取得へ置き換える。
取得権限は管理側だけが保持し、対象の問題リビジョンとテストセットを照合する。
バンドルの展開と期待出力の保持も管理側で行い、VMへは必要なケースの入力だけを渡す。
取り込み用のFargate検証タスクは、この決定の置き換え対象に含めない。

## 影響と未決事項

EC2ホスト、ゲストカーネル、Firecracker、isolateの更新と脆弱性対応を運用側で担う。
VM境界を設けても、脆弱性による脱出やゲスト内の計測器の侵害を排除できるわけではない。
ホストからの監視と異常系テストを含めて検証する。

次の事項は実装時に決める。

- KVMが利用できるEC2構成と、ネスト仮想化またはベアメタルの選択。
- ホストとゲストの固定イメージ、対応カーネル、Firecrackerとisolateの版。
- 計測のばらつき、CPU割り当て、同時実行数とメモリ余白。
- ホストとゲスト間の転送方式、監視期限、出力量と一時領域の上限。
- 採点の試行識別子、キューの再試行、結果保存の冪等性と障害回収。
